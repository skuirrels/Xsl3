# Xsl3 internals: what came from upstream, and how

This file records how Xsl3 was extracted from `dotnet/runtime` (SPEC §6.1) and everything that had to be
vendored, bridged or rewritten to make the engine build outside `System.Private.Xml`. Keep it current: the
weekly upstream-sync job (SPEC §6.4) diffs the upstream paths below against the fork point.

Vendored files are added with `eng/vendor.sh <runtime-checkout> <path under src/libraries> ...`, which keeps
the upstream-relative path.

## Rules for changes to upstream code

- Every change to a vendored or engine file is either one of the mechanical rewrites listed below, or is
  marked with a `// Xsl3:` comment that says why. `grep -rn "Xsl3:" src/Xsl3` lists them.
- Files keep their .NET Foundation licence header.
- The optimiser's `.p` pattern files are kept for documentation only; `XmlILOptimizerVisitor.cs` is the
  source of truth (SPEC §3.2.1).
- The raw writers' T4 templates are not kept; the generated C# is committed and edited directly (SPEC §3.2.5).

## Mechanical rewrites

Applied across the engine and vendored code when the fork was taken. Re-apply them when porting an upstream change.

| Rewrite | Why |
|---|---|
| Namespace `System.Xml.Xsl` → `Xsl3` (and its sub-namespaces) | SPEC §6.1 step 2 |
| `global using System; global using System.Xml;` (`GlobalUsings.cs`) | Upstream files resolved those through their enclosing `System.Xml.Xsl` namespace |
| `global using LocalAppContextSwitches = System.Xml.LocalAppContextSwitches;` | Same reason; `System.LocalAppContextSwitches` is also vendored |
| `XmlCollation.Windows.cs` + `XmlCollation.Unix.cs` → `XmlCollation.Platform.cs` | Upstream picks one at build time per target OS; Xsl3 ships one portable assembly, so it branches on `OperatingSystem.IsWindows()` |
| `new XmlAtomicValue(...)` → `XmlAtomicValueInternals.Create(...)` | The constructors are internal |
| `new XmlException(...)` → `XmlExceptionInternals.Create(...)` | The message-formatting constructors are internal; `Create` mirrors every constructor overload |
| `settings.OutputMethod = x` → `settings.SetOutputMethod(x)` | The setter is internal, and an extension can't add a setter to an existing property |
| `new XmlWriterSettings(XmlQueryDataReader)` → `XmlWriterSettingsInternals.Create(reader)` | Stock's constructor takes System.Private.Xml's own `XmlQueryDataReader` |
| Unqualified `UniqueIdTbl`, `NodeTypeLetter`, `GetKindMask` in `XPathDocumentNavigator` → `XPathNavigator.…` | They were inherited internal members; now static extension members, which need qualifying |
| `Globalization.CharUnicodeInfo` → `System.Globalization.CharUnicodeInfo` in `NumberFormatter` | Relied on the enclosing `System` namespace |
| `#if NET` → `#if NET9_0_OR_GREATER` in `HexConverter.ToString` | `string.Create` with a ref-struct state needs .NET 9 |
| Vendored `XPathDocument` renamed `InternalXPathDocument` (`internal sealed`) | So it never shadows the public `System.Xml.XPath.XPathDocument`, in Xsl3 or in assemblies that see its internals |

## Bridges: internal members of public types

The engine calls internal members of *public* System.Xml types. Those can't be vendored, because the public
type must stay the real one (`XslCompiledTransform.OutputSettings` returns a real `XmlWriterSettings` that
`XmlWriter.Create` must honour; users pass real `XmlReader`s and `XPathNavigator`s). `src/Xsl3/Bridges`
supplies them, mostly as C# 14 extension members with the original names so call sites compile unchanged.

Three techniques, in order of preference:

1. **Copy** the code when it only uses public API.
2. **`[UnsafeAccessor]`** when the behaviour lives in System.Private.Xml. It binds at JIT time, dispatches
   virtually, and works under trimming and NativeAOT (ILLink keeps the targets).
3. **Reflection**, only when a signature mentions a System.Private.Xml-internal type, which UnsafeAccessor
   can't express before .NET 10. Each use runs at most once per document or transformation, and carries
   `[DynamicDependency]` for the trimmer.

The shipped System.Private.Xml is itself IL-trimmed, so an internal member that exists in source may be gone
at run time (for example the `XmlWriterSettings.AutoXmlDeclaration` getter). Every accessor below was checked
against the .NET 8 and .NET 10 runtimes; the upstream test suite exercises all of them on both.

## The output path

Upstream's `XslCompiledTransform.Transform(…, Stream|TextWriter|string)` calls `XmlWriter.Create(results,
OutputSettings)`; `XmlILCommand.Execute` then unwraps the `XmlWellFormedWriter` to drive the stock raw writer
inside it directly. Those writer types are internal to System.Private.Xml, so:

- For **Stream, TextWriter and file** destinations, Xsl3 builds the same raw writer chain from its vendored
  writers (`XmlWriterSettingsInternals.CreateRawWriter`: raw text writer, plus `QueryOutputWriter` when
  the settings need it) and drives that. Output is byte-identical to stock; `Xsl3.Differential` checks it.
- For an **`XmlWriter` the caller supplies**, Xsl3 can't reach the raw writer inside it and uses upstream's
  own fallback, `XmlRawWriterWrapper`, which writes through the public `XmlWriter` API. Upstream takes the
  same path for any writer that isn't a stock well-formed writer at `WriteState.Start` with a non-`Document`
  conformance level. `Xsl3.Differential` compares this path with stock too; any difference found goes in
  `docs/divergences.md`.

Disposing a raw writer directly (upstream only ever closes one through `XmlWellFormedWriter`) calls
`Close(WriteState.Start)` once, which is what the well-formed writer does for a writer XSLT has bypassed.

## Other notable decisions

- **`XPathNodeIterator.count`** is an internal field that upstream's `ResettableIterator` copies and resets.
  Xsl3 leaves it alone: it starts at `-1`, so a cloned iterator recomputes `Count` on first use. Nothing in
  Xsl3 calls `ResetCount`.
- **`XmlQueryRuntime.DebugSetGlobalValue`** (debugger-only) used the internal `XmlAnyListConverter`; it now
  accepts only items and sequences of items.
- **AppContext switches** keep the stock names (`Switch.System.Xml.*`), so code that configured stock
  `XslCompiledTransform` through them configures Xsl3 the same way.

## Test infrastructure

`tests/Xsl3.Upstream.Tests` is regenerated by `eng/port-upstream-tests.py <runtime-checkout>`. The port
copies the tests unchanged apart from `System.Xml.Xsl` → `Xsl3`. dotnet/arcade's xunit extensions are not on
nuget.org, so `Shims/XunitExtensions.cs` provides `PlatformDetection`, `ConditionalFact`/`Theory`,
`ConditionalClass`, and the `PlatformSpecific`/`OuterLoop`/`ActiveIssue` category traits with arcade's
semantics. `Shims/AssemblyInfo.cs` disables test parallelization, as upstream's project does (the tests
share output file names).
